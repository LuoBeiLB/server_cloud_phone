## 1. 项目概述

本项目是**「X86 云手机群控平台」**的可运行 demo，依据《X86云手机平台_本月Demo详细计划_主流程跑通.md》实现，
定位对标商用产品**魔云腾**（其底座即 Redroid + Docker 安卓虚拟化）。

### 甲方五要素

甲方微信澄清的需求原文：**「x86 虚拟云手机 + 苹果 UI + 群控投屏客户端 + App 客户端 + 网站登录及管理系统，类魔云腾」**，
并补充**「云手机只要求浏览器能打开网页即可」「这个月先做出来看看效果」「主流程跑通就可以了」**。

| # | 甲方要素 | 本仓库交付 | 开源件 |
|---|---|---|---|
| 1 | x86 虚拟云手机 | Redroid 实例 + Chromium + iOS 皮肤 + 一机一码 | Redroid / Chromium / Lawnchair |
| 2 | 苹果 UI | 皮肤级（启动器主题 + 图标 + 壁纸 + 毛玻璃 Dock） | Lawnchair + 主题包 |
| 3 | 群控投屏客户端 | Web 多画面预览 + 单台操控 + 批量同步 | STF / minicap / minitouch |
| 4 | App 客户端 | 安卓 App（Kotlin + Compose）：登录 / 设备列表 / 投屏 / 批量 | 自研（复用后端 API） |
| 5 | 网站登录及管理系统 | Web：登录 + 设备管理 + 分组 + 批量下发 | FastAPI + Vue3 |

> **关键简化**：因甲方明确「浏览器开网页即可」，最大死穴——ARM 转译 + 重 App 风控——基本消失。
> Chromium 在 x86/arm 安卓上原生跑，无需 libndk/libhoudini 转译层。

### 本月 demo 目标（主流程闭环）

```
登录 Web 管理系统
   → 批量建 N 台云手机（显示 iOS 皮肤）
   → 每台浏览器打开指定网页
   → 每台呈现独立设备标识 / 独立出口 IP / 独立浏览器指纹
   → Web 端 & PC 端多画面预览 + 单台实时操控
   → 批量：一键让所有设备打开同一网页 / 同步操作（1 控 N）
   → App 客户端也能看设备、做基础操控
   → 录一段脚本 → 跨设备回放
```

demo 的核心工程价值在于**可插拔设备后端**：整套业务闭环在没有 Docker/Redroid 的机器（macOS/Windows）
上也能端到端跑通（simulator 后端）；迁到 Linux 宿主机后只改一个环境变量 `CLOUD_DEVICE_BACKEND=redroid`
即变成真实云手机，业务代码 / API 契约 / 三端客户端**零改动**。

## 2. 系统架构

### 2.1 分层图

```
┌───────────────────────────────────────────────────────────────────┐
│  接入端                                                             │
│  Web 控制台(Vue3)     PC 客户端(Electron)     App 客户端(Kotlin)    │
└──────────────┬──────────────────┬────────────────────┬─────────────┘
               │ REST  /api        │ 同一套 API 契约     │
               │ WS    /api/ws     │                    │
┌──────────────▼──────────────────────────────────────▼──────────────┐
│  平台后端 (FastAPI, :8000)                                          │
│  鉴权(JWT) · 设备/分组 CRUD · 一机一码 · 单机操控 · 批量(1控N) ·    │
│  脚本录制回放 · WebSocket(设备状态/批量进度/预览帧广播)             │
└──────────────┬──────────────────────────────────────────────────────┘
               │ DeviceBackend 抽象（orchestrator/base.py，可插拔）
               │ 一键切换开关：环境变量 CLOUD_DEVICE_BACKEND
        ┌──────┴───────┐
        ▼              ▼
  SimulatorBackend  RedroidBackend
  (内存态 + SVG预览) (Docker SDK + Redroid + adb + screencap)
        │              │
        ▼              ▼
   任意平台         Linux 宿主机
   (演示/开发)      (真实 x86/arm 安卓实例)
```

### 2.2 可插拔设备后端

上层（`routers/` → `services.py`）只依赖 `backend/app/orchestrator/base.py` 里的抽象基类
`DeviceBackend`。`get_backend()` 按配置返回具体实现：

```python
# backend/app/orchestrator/base.py
def get_backend() -> DeviceBackend:
    if settings.device_backend == "redroid":
        from .redroid import RedroidBackend
        return RedroidBackend()
    from .simulator import SimulatorBackend
    return SimulatorBackend()
```

| 维度 | SimulatorBackend | RedroidBackend |
|---|---|---|
| 运行前提 | 无（纯 Python 内存态） | Linux + Docker + adb + binder 内核模块 |
| 适用平台 | macOS / Windows / Linux | Linux 宿主机（或 arm64 Linux VM） |
| 实例载体 | 进程内 `_runtime` 字典 | `docker run redroid/redroid:...` 容器 |
| 画面来源 | `preview.render_frame()` 渲染 SVG（440×820 iOS 皮肤） | `adb exec-out screencap -p` 真机截图 |
| 操控通道 | 改内存态 | `adb shell input tap/swipe/text/keyevent` |
| 切换方式 | `CLOUD_DEVICE_BACKEND=simulator`（默认） | `CLOUD_DEVICE_BACKEND=redroid` |

### 2.3 关键数据流

- **建机**：`POST /api/devices/batch` → `services.create_device()` 生成一机一码（`fingerprint.py`）
  → `backend.create()/start()/open_url()` → 落库 → WS 广播 `device_status`。
- **预览**：前端 WS 发 `subscribe{device_ids,fps}` → `routers/ws.py` 周期性调 `backend.screenshot()`
  渲染帧 → 推 `preview`；前端同时对单机/少量设备做 HTTP `/screenshot` 高频轮询兜底。
- **批量/同步**：`POST /api/batch/*` → 并发对选中设备执行 → 每台完成推 `batch_progress`；
  同步操控在 `batch._scale()` 做跨分辨率坐标折算。
- **脚本**：前端在单机操控页把动作序列收集为 `steps` → `POST /api/scripts/{id}/run`
  在多台设备并发回放 → 产出逐设备逐步骤报告 → 推 `script_done`。

## 3. 技术栈

| 层 | 选型 | 版本/说明 |
|---|---|---|
| 后端框架 | **FastAPI** + Uvicorn | fastapi≥0.115，uvicorn[standard]≥0.30，监听 8000 |
| ORM/DB | **SQLAlchemy 2 (async)** | dev 用 aiosqlite(SQLite)，生产用 asyncpg(PostgreSQL) |
| 鉴权 | **PyJWT** + hashlib.pbkdf2 | HS256，密码 pbkdf2_sha256（200000 轮，避开 bcrypt 原生编译） |

| 实时 | **WebSocket**（FastAPI 原生） | `/api/ws`，广播 + 按订阅推预览帧 |

## 5. 快速开始

### 5.1 方式 A：simulator 模式（任意平台，无需 Docker，推荐先跑）

**后端**（Python 3.10+）：

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install fastapi "uvicorn[standard]" "sqlalchemy[asyncio]" aiosqlite \
    pydantic pydantic-settings PyJWT python-multipart httpx
uvicorn app.main:app --reload            # http://localhost:8000/docs
```

首次启动会自动建表（SQLite `cloud_platform.db`）并播种管理员账号。

**前端**（Node 18+，另开终端）：

```bash
cd frontend && npm install && npm run dev   # http://localhost:5173
```

Vite 已把 `/api`（含 WebSocket）反代到 `http://127.0.0.1:8000`（见 `vite.config.js`），
先起后端再起前端即可，无需改地址。

**默认账号**：`admin / admin123`（`config.py` 的 `admin_username/admin_password`，首启自动播种）。

**一键验证 8 条验收**（后端已启动的前提下）：

```bash
cd backend && source .venv/bin/activate && python -m tests.smoke
```

`tests/smoke.py` 会自动跑完 登录 → 批量建 10 台 → 抽查 3 台指纹互不相同 → 预览帧 →
单机操控 → 批量同步 → 分组 → 脚本跨设备回放，全绿即主流程跑通。
（注意它用 `httpx.Client(..., trust_env=False)` 绕开本机代理，见 [FAQ](#13-排障-faq)。）

### 5.2 方式 B：Docker Compose 一键起整套

```bash
docker compose up -d --build          # postgres:15 + redis:7 + backend + frontend
```

访问：

| 服务 | 地址 |
|---|---|
| 前端管理系统 | http://localhost:5173 |
| 后端 API 文档 | http://localhost:8000/docs |
| 初始管理员 | admin / admin123 |

compose 内后端默认 `CLOUD_DEVICE_BACKEND=redroid`（真机，与生产一致），数据库自动指向内置 postgres
（`postgresql+asyncpg://cloud:cloud@postgres:5432/cloud`），前端由 nginx 托管并反代 `/api`、`/api/ws`。

停止 / 清库：

```bash
docker compose down          # 停服务，保留数据卷
docker compose down -v       # 连同 postgres/redis 数据卷一起删
```

### 5.3 方式 C：真实 Redroid

**C-1. Linux 宿主机（Intel/AMD 裸机，最终形态）**：

```bash
sudo bash deploy/scripts/host-setup.sh        # binder/ashmem 内核模块 + docker + adb + scrcpy
cd backend
export CLOUD_DEVICE_BACKEND=redroid
export CLOUD_REDROID_GPU_MODE=host            # Intel/AMD 核显；NVIDIA/无核显用 guest
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

**C-2. 本机 Apple Silicon（经 Lima arm64 VM）**：见 [§10.3](#103-真机部署linux--lima-vm) 完整步骤，
或直接：

```bash
bash deploy/scripts/connect-vm-redroid.sh     # VM 内起 redroid 后端 + SSH 隧道回 Mac:8000
cd frontend && npm run dev                     # http://localhost:5173（admin/admin123）
bash deploy/scripts/connect-vm-redroid.sh --revert   # 切回 simulator
```

## 6. 完整 API 参考

- **Base URL**：`http://<host>:8000`，所有业务接口前缀 `/api`（`settings.api_prefix`）。
- **鉴权**：除 `POST /api/auth/login` 外，所有 `/api/devices`、`/api/groups`、`/api/control`、
  `/api/batch`、`/api/scripts` 路由都要求 `Authorization: Bearer <token>`（`get_current_user` 依赖）。
- **在线文档**：`http://<host>:8000/docs`（FastAPI 自动生成的 Swagger UI）。

### 6.0 根 / 健康检查（无需鉴权）

| 方法 | 路径 | 响应 |
|---|---|---|
| GET | `/` | `{name, backend, docs:"/docs", ws_clients}` |
| GET | `/api/health` | `{status:"ok", backend}` |

### 6.1 鉴权 `/api/auth`

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| POST | `/api/auth/login` | `{username, password}` | `TokenResponse` |
| GET | `/api/auth/me` | —（Bearer） | `UserOut` |

```jsonc
// TokenResponse
{ "access_token": "<jwt>", "token_type": "bearer",
  "user": { "id": 1, "username": "admin", "role": "superadmin" } }
// UserOut
{ "id": 1, "username": "admin", "role": "superadmin" }
```

登录失败（用户名/密码错误）返回 `401`；token 失效同样返回 `401`（前端 axios 拦截器自动登出）。

### 6.2 设备分组 `/api/groups`（Bearer）

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| GET | `/api/groups` | — | `list[GroupOut]` |
| POST | `/api/groups` | `{name, parent_id?}` | `GroupOut` |
| DELETE | `/api/groups/{group_id}` | — | `{ok:true}` |

```jsonc
// GroupOut
{ "id": 1, "name": "矩阵A组", "parent_id": null, "device_count": 3 }
```

删除分组会先把组下设备 `group_id` 解绑为 null，再删组。

### 6.3 设备 `/api/devices`（Bearer）

| 方法 | 路径 | 请求体 / 查询 | 响应 |
|---|---|---|---|
| GET | `/api/devices` | 查询 `group_id`、`status`、`q`(名称模糊) | `list[DeviceOut]` |
| POST | `/api/devices` | `DeviceCreate` | `DeviceOut` |
| POST | `/api/devices/batch` | `DeviceBatchCreate` | `list[DeviceOut]` |
| GET | `/api/devices/{id}` | — | `DeviceOut` |
| PATCH | `/api/devices/{id}` | `{name?, group_id?}` | `DeviceOut` |
| DELETE | `/api/devices/{id}` | — | `{ok:true}` |
| POST | `/api/devices/{id}/start` | — | `DeviceOut` |
| POST | `/api/devices/{id}/stop` | — | `DeviceOut` |
| POST | `/api/devices/{id}/restart` | — | `DeviceOut` |
| GET | `/api/devices/{id}/screenshot` | — | `{device_id, frame}` |

```jsonc
// DeviceCreate（单台，未传 name 时后端生成「云手机-NNN」）
{ "name": null, "group_id": null, "width": 1080, "height": 1920,
  "dpi": 480, "target_url": null, "proxy": null }

// DeviceBatchCreate（一键建 N 台；count 取值 1–100）
{ "count": 10, "name_prefix": "云手机", "group_id": null,
  "width": 720, "height": 1280, "dpi": 320,
  "target_url": null, "auto_start": true }

// DeviceOut
{ "id": 1, "name": "演示机-001", "group_id": null, "status": "running",
  "adb_port": 6001, "width": 720, "height": 1280, "dpi": 320,
  "current_url": "https://example.com", "fingerprint": { /* 见 §7 */ },
  "created_at": "...", "updated_at": "..." }
```

`status` 取值：`creating` / `running` / `stopped` / `error`（`models.DeviceStatus`）。
`screenshot` 返回的 `frame` 是可直接放进 `<img src>` 的 data URL（simulator 为 `data:image/svg+xml;base64,...`，
redroid 为 `data:image/png;base64,...`）。

### 6.4 单机操控 `/api/devices/{device_id}/control`（Bearer）

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| POST | `.../control/open_url` | `{url}` | `{ok:true, url}` |
| POST | `.../control/tap` | `{x, y}` | `{ok:true}` |
| POST | `.../control/swipe` | `{x1, y1, x2, y2, duration_ms=300}` | `{ok:true}` |
| POST | `.../control/text` | `{text}` | `{ok:true}` |
| POST | `.../control/key` | `{key}` | `{ok:true}` |
| POST | `.../control/install` | `{apk_url}` | `{ok:true}` |

`key` 取值：`back` / `home` / `menu` / `recent` / `power` / `wake` / `enter` /
`volume_up` / `volume_down`（`redroid.py` 的 `_KEYCODES` 映射；`home` 走 HOME intent 以兼容 AOSP GSI）。

### 6.5 批量操作 / 同步操控 `/api/batch`（Bearer）

全部接受 `device_ids: list[int]` 并返回 `BatchResult`；`tap/swipe` 会按 `_scale()` 做跨分辨率折算
（参考分辨率 1080×1920 → 目标设备 width/height）。

| 方法 | 路径 | 请求体（在 `device_ids` 基础上追加） |
|---|---|---|
| POST | `/api/batch/open_url` | `url` |
| POST | `/api/batch/tap` | `x, y` |
| POST | `/api/batch/swipe` | `x1, y1, x2, y2, duration_ms=300` |
| POST | `/api/batch/text` | `text` |
| POST | `/api/batch/key` | `key` |
| POST | `/api/batch/install` | `apk_url` |

```jsonc
// BatchResult
{ "total": 10, "ok": 10, "failed": 0,
  "details": [ {"device_id": 1, "name": "演示机-001", "ok": true}, ... ] }
```

执行期间每台完成都会 WS 广播 `batch_progress`（见 [§6.7](#67-websocket-apiws)）。

### 6.6 脚本录制 / 回放 `/api/scripts`（Bearer）

| 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|
| GET | `/api/scripts` | — | `list[ScriptOut]` |
| POST | `/api/scripts` | `ScriptCreate` | `ScriptOut` |
| GET | `/api/scripts/{id}` | — | `ScriptOut` |
| DELETE | `/api/scripts/{id}` | — | `{ok:true}` |
| POST | `/api/scripts/{id}/run` | `{device_ids: [int]}` | `ScriptRunOut` |
| GET | `/api/scripts/runs/{run_id}` | — | `ScriptRunOut` |

```jsonc
// ScriptCreate（步骤模型对齐 Airtest .air 抽象）
{ "name": "开网页并操作", "description": "",
  "steps": [
    { "action": "open_url", "params": { "url": "https://whoer.net" } },
    { "action": "wait",     "params": { "seconds": 0.1 } },
    { "action": "swipe",    "params": { "x1": 540, "y1": 1600, "x2": 540, "y2": 600 } },
    { "action": "tap",      "params": { "x": 300, "y": 500 } }
  ] }

// ScriptRunOut（逐设备、逐步骤报告）
{ "id": 1, "script_id": 1, "status": "success",
  "results": [
    { "device_id": 1, "name": "演示机-001", "status": "success",
      "steps": [ {"action":"open_url","ok":true}, ... ] }
  ],
  "created_at": "..." }
```

`action` 支持：`open_url` / `tap` / `swipe` / `text` / `key` / `wait`
（`wait` 的 `seconds` 上限 10s）。回放完成推 WS `script_done`。

### 6.7 WebSocket `/api/ws`

单一端点，同时承担「广播」与「按订阅推预览帧」两职。

**客户端 → 服务端**（订阅预览帧）：

```jsonc
{ "type": "subscribe", "device_ids": [1, 2, 3], "fps": 1 }
```

**服务端 → 客户端**（消息类型）：

| type | 触发时机 | 载荷 |
|---|---|---|
| `device_status` | 设备创建/启停/改名/操控后状态变化 | `{ "device": DeviceOut }` |
| `device_removed` | 设备被删除 | `{ "device_id": <id> }` |
| `preview` | 预览循环按 fps 周期推帧 | `{ "device_id": <id>, "frame": "data:image/...;base64,..." }` |
| `batch_progress` | 批量任务每台完成 | `{ "action": "open_url", "done": 3, "total": 10 }` |
| `script_done` | 脚本回放结束 | `{ "run_id": 1, "status": "success" }` |

服务端预览循环 `interval = max(0.3, 1.0/fps)`（最低 300ms/帧）。前端 `src/api/ws.js`
自动重连（断线后 1.5s 重连），`src/stores/devices.js` 把 WS 帧与 HTTP 轮询做双通道兜底。

## 7. 一机一码机制

`backend/app/fingerprint.py` 的 `generate_fingerprint(seed, proxy)` 用一个稳定 `seed`（默认 `uuid4().hex`）
派生三组互不相同的字段，保证**同设备重启一致、设备间互不相同**（对应验收第 4 条「独立身份」）。
返回值同时带回 `seed` 便于复现。

### 三组字段

**1) 设备标识（`device`，作为 Redroid props 注入）**

| 字段 | 生成方式 | 举例 |
|---|---|---|
| `brand` / `manufacturer` / `model` / `marketing_name` | 从 10 款机型库随机（Pixel/Galaxy/小米/一加/OPPO/vivo/华为…） | `google/Google/Pixel 6` |
| `android_id` | `sha1("aid-"+seed)[:16]` | `a1b2c3...` |
| `serialno` | `"SN"+sha1("sn-"+seed)[:10].upper()` | `SN1A2B3C4D5E` |
| `imei` | 15 位随机数字 | `86xxxxxxxxxxxxx` |
| `mac` | 6 段随机十六进制 | `ac:1f:...` |
| `android_version` | 12 / 13 / 14 随机 | `13` |

**2) 浏览器指纹（`browser`，注入 Chromium）**

`user_agent`、`chrome_version`（118/120/121/122）、`width/height`、`dpi`、
`device_pixel_ratio`（=dpi/160）、`timezone`（8 个时区随机）、`language`（zh-CN/en-US/ja-JP…）、
`webgl_vendor`（Qualcomm/ARM/Google Inc./Imagination）、`webgl_renderer`（Adreno/Mali/PowerVR）、
`canvas_noise_seed`（`sha1("canvas-"+seed)[:12]`，供注入脚本对每台做固定微扰）、
`hardware_concurrency`（4/6/8）、`device_memory`（4/6/8/12）。

**3) 网络出口（`network`）**

`proxy`（从 `CLOUD_PROXY_POOL` 分配的代理位，可为空）、`exit_ip`（demo 展示用的独立出口 IP）。

### Redroid props 注入

`redroid_props(fp)` 把设备标识转成 Redroid 启动参数（只注入设备标识，
显示参数 width/height/dpi 由设备记录单独指定，避免与浏览器指纹分辨率冲突）：

```
ro.product.brand=<brand>
ro.product.manufacturer=<manufacturer>
ro.product.model=<model>
ro.product.name=<model>
ro.serialno=<serialno>
androidboot.serialno=<serialno>
```

> **深度改机边界**：`android_id` 无法用 prop 改，需启动后 `adb shell settings put secure android_id`
> 写入（见 `deploy/redroid/start-instance.sh`）；`IMEI`、`MAC` 的深度伪造需 Magisk/LSPosed 模块，
> 属长期运维项，不在本月 demo 范围。

## 8. 设备编排

### 8.1 生命周期抽象

`DeviceBackend`（`orchestrator/base.py`）定义了两类方法：
生命周期 `create / start / stop / destroy`，操控 `open_url / tap / swipe / input_text / key / install / screenshot`。
`create()` 返回 `Provisioned{backend_ref, adb_port}`。`services.py` 负责把「DB + 后端 + 指纹 + WS 广播」串起来：

```python
# services.create_device（简化）
fp = generate_fingerprint(proxy=proxy or _pick_proxy())
device = Device(..., fingerprint=fp, status=creating); commit
prov = await backend.create(device)      # 拿到 backend_ref / adb_port
if auto_start:
    await backend.start(device)
    if target_url: await backend.open_url(device, target_url)
    device.status = running
await broadcast_device(device)           # WS device_status
```

后端拉起失败会把该设备标记为 `error`，不阻塞批次里的其它设备。

### 8.2 SimulatorBackend

维护进程内 `_runtime: dict[device_id, {...}]`，记录每台的当前页面与最近一次操作。
所有操控/批量/脚本都会真实改变这份状态，因此 Web 多画面、单机操控、批量同步、脚本回放
在 demo 中都能被肉眼验证。`screenshot()` 调 `preview.render_frame()` 渲染一张 440×820 的 SVG
（无 `current_url` 时画 iOS 主屏，有则画 Chromium 浏览器页并叠加一机一码信息），返回 base64 data URL。
`create()` 分配的 adb_port 从 6001 起自增（仅占位）。

### 8.3 RedroidBackend

仅在 `CLOUD_DEVICE_BACKEND=redroid` 时被导入（`docker` SDK 延迟导入，避免非 Linux 环境报错）。

- **create()**：`docker.containers.run(image, command=[...], privileged=True, ...)`。
  - 端口：宿主 `5555 + device.id` → 容器 `5555/tcp`。
  - 数据卷：`{CLOUD_REDROID_DATA_DIR}/inst{id}:/data`。
  - command 注入 `androidboot.redroid_gpu_mode/width/height/dpi` + 一机一码 props。
  - 有代理时注入容器 `HTTP_PROXY/HTTPS_PROXY`。
  - 先清理可能残留的同名容器 `redroid_{id}`。
- **start()**：`container.start()` 后**轮询等 `getprop sys.boot_completed==1`**，最多约 180s
  （90 次 × 2s，首次冷启 dex 优化约 30–60s），期间反复 `adb connect localhost:{port}`。
- **操控**：`adb -s localhost:{port} shell input tap/swipe/text/keyevent`，
  `open_url` 走 `am start -a android.intent.action.VIEW -d <url>`。
- **screenshot()**：`adb exec-out screencap -p` 取真机 PNG → base64；失败时回退到 SVG 渲染兜底。

> `deploy/redroid/start-instance.sh` 与 `RedroidBackend` **行为对齐**（同样的容器命名 `redroid_{id}`、
> 端口 `5555+id`、数据目录 `inst{id}`、props 注入），可用脚本单独验证后端逻辑。

## 9. 实时预览与操控

### 9.1 预览双通道（WS 推送 + HTTP 轮询兜底）

`src/stores/devices.js` 的 `subscribePreviews(ids, fps)` 同时启用两条通道，互为兜底：

1. **WebSocket 推送**（快）：`subscribe` 后由后端 `_preview_loop` 周期推 `preview` 帧。
2. **HTTP 轮询**（稳）：轮询 `GET /api/devices/{id}/screenshot`，走 axios + Vite 代理，一定通。

策略：
- **单机 / 少量设备（≤3，如单机操控页）**：`force=true`，直接高频 HTTP 轮询保证实时，不被 WS 抑制。
  后端 `/screenshot` **实测约 64ms**（`devices.js` 注释），单机操控页按 **~5fps** 订阅（`Control.vue`），
  切页/翻页的画面刷新在**约 400ms 内**可见。
- **多设备（网格）**：WS 优先；当近 2.5s 内收到过 WS 帧则认为 WS 健康，自动跳过 HTTP 轮询，避免重复请求。
  网格页 `Grid.vue`、批量页 `Batch.vue` 按 **1fps** 订阅。

### 9.2 坐标映射

前端画面尺寸与设备真实分辨率不同，`PhoneFrame.vue` 在点击时按比例折算成设备坐标：

```js
const rx = (e.clientX - rect.left) / rect.width
const ry = (e.clientY - rect.top)  / rect.height
emit('tap', { x: Math.round(rx * device.width),
              y: Math.round(ry * device.height) })
```

批量同步操控则在后端 `batch._scale()` 再做一次跨分辨率折算
（主控坐标按参考 1080×1920 → 每台目标设备 width/height），实现「1 控 N」下不同分辨率也点得准。

### 10.3 真机部署（Linux / Lima VM）

> ⛔ **宿主内核硬门槛（三条，缺一不可，应用层都绕不过）**
>
> | 门槛 | 检查 | 缺失时的现象 |
> |---|---|---|
> | binder 三件套 | `ls -l /dev/binder /dev/hwbinder /dev/vndbinder` | 容器起不来，日志报 binder 相关 |
> | **SELinux（selinuxfs）** | `ls -d /sys/fs/selinux` 或 `grep selinuxfs /proc/filesystems` | 容器 `exited` **退出码 129**、`docker logs` **完全为空**，真正错误只在宿主 `dmesg`：`init: mount("selinuxfs"…) failed` |
> | cgroup v1 层级 | `stat -fc %T /sys/fs/cgroup`（`cgroup2fs` = 纯 v2） | 宿主 dmesg 报 `cgroup: Unknown subsys name 'memory'` |
>
> **实测（2026-07-30）**：同一台 Mac 上两种虚拟化，结论相反 ——
>
> | 环境 | 内核 | binder | SELinux | redroid |
> |---|---|---|---|---|
> | OrbStack | `7.0.11-orbstack` | ✅ 三件套齐 | ❌ 无 | ❌ 退出码 129，日志全空 |
> | **Lima + Ubuntu 26.04** | `7.0.0-28-generic` | ✅ binderfs | ✅ `CONFIG_SECURITY_SELINUX=y` | ✅ **跑通** |
>
> Lima 上实测：Android 12 / SDK 31 / arm64-v8a / 80 进程 / 96 应用包 / 单实例约 1 GiB，
> adb screencap 取到 720×1280 真实画面。所以准确说法是「**OrbStack 等裁剪内核不行**」，
> 而不是「macOS 不行」。macOS 开发机一键脚本：`deploy/scripts/dev-up-real.sh`。
> 三条门槛已全部纳入 `/api/diagnostics`（见 [§12.5](#125-故障可见性设计禁止静默失败)）；
> 后端在容器内时它们显示为「无法判定」，需按提示在宿主机上确认。

## 11. 真机接入与实测

`docs/redroid-real-benchmark.md` 是在**真实 Android 实例**（非 simulator）上跑出的实测数据。
环境：Apple Silicon Mac（M 系列，16G）→ Lima/Apple 虚拟化起 arm64 Ubuntu VM（6 vCPU / 8G）→ Docker + Redroid。

### 关键实测（Android 12, arm64-v8a）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 启动 | `boot_completed=1`，Android 12 | 真机完整启动 |
| CPU 架构 | ABI=`arm64-v8a`，`native.bridge=0` | **原生 arm 执行，零转译**（无 libndk/houdini） |
| 单实例内存 | **~555–580 MiB** | 稳态 RSS |
| 单实例 idle CPU | 0.4–1.4% | 空闲极低 |
| adb 往返延迟 | **7 ms/次** | 控制通道低延迟 |
| input tap 注入 | 33 ms/次 | 触控注入实时 |
| GL 渲染器 | ANGLE / Vulkan(**SwiftShader**) / GLES 3.1 | **软件渲染**（VM 无 GPU 直通） |
| 浏览器 | 内置 **Chromium WebView 125** + webview_shell + htmlviewer | `am start VIEW` 成功，demo 核心用例达标 |
| 5 台并发密度 | 5×~580MiB = 3.9G / 7.7G | 内存维度宽裕；启动瞬时 CPU 冲高（dex2oat） |

单实例按 ~580MiB 外推，8G VM 留 20% 余量约可跑 11–12 台（仅内存维度）。
**生产裸机（更大内存 + Intel/AMD host GPU）密度显著更高**；正式容量以目标裸机 + host GPU
复测 `deploy/scripts/redroid-benchmark.sh` 为准。

### Apple Silicon 必用 64only 镜像（关键坑）

M 系列 CPU **不支持 32 位 ARM 执行**。混合镜像 `redroid/redroid:12.0.0-latest` 里的 32 位
`app_process32`/`mediaserver` 会 `Exec format error`（实测 227 次），导致 **zygote 崩溃循环、永远 boot 不完**。
必须换 **`redroid/redroid:12.0.0_64only-latest`**（这正是 `config.py` / `.env.example` / 各脚本的默认值），换后一次点亮。

### 已验证的全链路（真机）

## 12.5 故障可见性设计（禁止静默失败）

甲方是 `docker compose up` 一键跑起来的，既不熟 docker 也进不了宿主机。因此本项目把
「任何失败都必须在界面上说清原因与处置」当作硬约束。分四层实现：

### 12.5.1 第一入口：系统自检

`GET /api/diagnostics`（需登录）+ 前端「系统自检」页（`/#/diagnostics`）。逐项实测并给出
`status(ok|warn|fail|unknown|skip)` + 实测值 + 原因 + **可执行的处置**：设备后端、数据库、
Redis、Docker daemon、redroid 镜像、内核 binder、`/dev/dri`、adb、磁盘、内存、
设备失败记录、库中状态与容器真实状态的一致性。需要动手的项排在最前。

> ⚠️ **关于 `unknown`**：后端跑在容器里时，宿主的内核设施（binder、`/dev/dri`）在容器命名
> 空间内本来就看不见。这类项报 `unknown` 而**不是** `fail`，并提示「容器里看不到不等于宿主
> 没有，请在宿主机自行确认」。把假阴性报成 fail 会把人引向错误方向去改内核。响应里的
> `probed_from` / `in_container` 标明探测位置。

`GET /api/health` 保持免鉴权且轻量（compose healthcheck 用它），但**包含数据库状态** ——
库挂了会导致 seed/登录失败、自检页根本进不去，此时它是唯一能指出「问题在数据库」的地方。

### 12.5.2 后端：拉不起来必须抛异常且带处置

`orchestrator/base.py` 三类异常，语义严格区分，路由层各自映射：

| 异常 | 含义 | HTTP | 排障方向 |
|---|---|---|---|
| `DeviceProvisionError` | 云手机**压根没建/起成功** | 502 | 宿主环境：镜像、binder、/dev/dri、docker.sock、内存 |
| `DeviceUnreachable` | 已建好的设备**失联** | 503 | adb 与容器状态 |
| `DeviceCommandError` | 设备活着，**这条命令**失败 | 502 | 路径/权限/包名 |

`DeviceProvisionError` 强制携带 `stage`(env/provision/start/boot) + `reason` + `hint` +
`evidence`（容器状态、退出码、OOMKilled、容器日志尾部），并按特征把 docker/系统报文翻译成
中文原因与命令（镜像未拉 → `docker pull ...`；日志含 binder → 装 `linux-modules-extra` 并
`modprobe`；OOMKilled → 按 1.5 GiB/台 规划内存）。

⛔ 两个**曾经存在的静默降级**（回归时务必守住）：
- `redroid.start()` 等 `sys.boot_completed` 的循环耗尽后曾直接 `return`，调用方把
  「Android 根本没起来」当成启动成功、设备标记 `running`，后续每个操作都失败而界面显示正常；
- `services.create_device` 曾用空的 `except Exception: 标记 error`，原因整个丢失，界面上
  只有「状态：异常」三个字。现在原因写入 `Device.last_error`（原因 ｜ 处置 ｜ 证据），
  随 `DeviceOut` 返回，设备列表「状态」列的红色图标悬浮即可查看。

另注：`RedroidBackend` 的 docker 客户端是**惰性连接**的。`services.py` 在模块导入时就
`get_backend()`，若构造函数里连 docker 并抛异常，整个后端进程起不来 —— 甲方看到的会是
backend 容器崩溃重启，而不是界面上一句「Docker 不可用，请挂载 docker.sock」。

### 12.5.3 前端：全局兜底，永不静默

`api/client.js` 的响应拦截器：
- 401 → 清 token + 清 store + 回登录页（只清 localStorage 不够，路由守卫读的是 store）；
- 503 `unreachable` → 按设备节流提示失联；
- **其余任何失败** → `describeError()` 整理成一句「原因 + 处置」（后端给了 `hint` 就带上；
  502/503/504 且无 JSON body 时直接给 compose/nginx 的排查步骤），然后延迟 260ms 兜底弹出。
  「是否已提示过」以 DOM 中有无 `.el-message` 判断：业务自己的 `catch` 弹过就让位。
  取舍是多个请求同时失败只保证至少一条提示 —— 相比静默，少弹一条重复提示可以接受。
- `/screenshot`、`/skin/applying`、`/metrics` 等高频轮询不参与兜底，避免断网刷屏；它们的
  失败由预览画面冻结 + WS 断线横幅体现。

### 12.5.4 前端：通道与资源层的可见性

- **WS 断线**：`api/ws.js` 暴露 `onState`，状态同步到 store，`MainLayout` 顶部显示
  「实时通道已断开，画面与设备状态可能不是最新（已重连 N 次）」并链到系统自检。
  不做这个的话，WS 断了只是预览静止、状态不更新，用户体验到的是「操作没反应」。
  重连改为退避（1.5s 起、最多 10s），避免长时间不可用时刷屏。
- **懒加载 chunk 拉取失败**：所有页面都是 `() => import()`，文件名带内容哈希。重新发布后旧
  chunk 消失，若浏览器还缓存着旧 `index.html`，动态 import 被拒 → 导航静默中止 → 页面空白。
  两侧都修：nginx 让缺失资源真 404（不再回退成 `200` + HTML）且 `index.html` 禁缓存；
  `router.onError` 识别该错误后提示并自动刷新一次，10s 内再次失败则改为提示手动强刷，
  不做无限刷新。

## 12.6 iOS 皮肤：壁纸里不能画 Dock 底板（回归守则）

⛔ 早期的皮肤壁纸把 **Dock 的半透明圆角底板和页面指示点直接画进了 PNG**。它是按
720×1280 固定位置的静态美术，而真实 Dock 图标由 Lawnchair 按设备几何排布。实测
（redroid，物理 720×1280 被 `wm size` override 成 1080×1920）：

| | 位置 |
|---|---|
| 壁纸里画的底板（图内 y≈963..1125）映射到 1920 高 | y ≈ 1485..1680 |
| Lawnchair 实际 Dock 图标（`uiautomator dump` 实测） | **y = 1648..1888** |

图标比底板低约 170px 且顶到屏幕底边，肉眼即「Dock 里四个应用偏移跑出了底板」。
分辨率 / 密度 / 导航栏形态任意一项变化都会破坏对齐 —— 假底板注定对不准。

**结论：壁纸只放渐变。** Dock 底板要么交给启动器自己画，要么不要。
清理脚本（纯标准库，无需 Pillow）：

```bash
python3 deploy/ios-skin/strip-dock-plate.py backend/app/skins/wallpaper_*.png
```

它按「水平方向硬边」定位画上去的元素（不能用中心-边缘差值判断：斜向渐变本来就处处有差，
会把大半张图误判掉），再用区间上下两行逐像素插值还原渐变；检出区间超过画面 25% 则放弃不改。

> 注：`preview.py` 给 simulator 渲染的 SVG 里画 Dock 底板**没有这个问题** ——
> 底板与图标由同一段代码在同一坐标系里绘制，天然对齐。

## 13. 排障 FAQ

**Q0. 任何异常先开「系统自检」页（`/#/diagnostics`）。** 它会逐项实测并直接给出处置命令，
比翻日志快得多。设计与各检查项含义见 [§12.5](#125-故障可见性设计禁止静默失败)。

**Q1. 本机代理劫持 localhost，导致 curl/WS 返回 502 或超时。**
开了系统代理/企业代理时，`localhost`、`127.0.0.1` 的请求可能被代理拦截。对策：
- Python 端：`httpx.Client(trust_env=False)`（`tests/smoke.py` 已这么做）；
- curl：`curl --noproxy 127.0.0.1 http://127.0.0.1:8000/api/health`（`vm-run-backend.sh`/`connect-vm-redroid.sh` 已这么做）；
- 通用：`export NO_PROXY=localhost,127.0.0.1`。

**Q2. 前端预览白屏。**
`PhoneFrame.vue` 的占位图**不能用 `btoa()`**——它无法编码中文（"加载中…"）会抛
`InvalidCharacterError`，导致整个组件渲染失败、预览页白屏。已改用 `encodeURIComponent` 生成
data URL 以支持 Unicode（见 `frontend/src/components/PhoneFrame.vue`）。

**Q3. 开发时编辑 Pinia store 导致运行中页面状态损坏 / 子路由白屏。**
`stores/auth.js` 与 `stores/devices.js` 均已加 `acceptHMRUpdate`
（`if (import.meta.hot) import.meta.hot.accept(acceptHMRUpdate(useStore, import.meta.hot))`），
使 store 支持热更新，避免热替换时状态错乱。

**Q4. Redroid 在 Apple Silicon 上 boot 不完 / zygote 崩溃循环。**
必须用 `redroid/redroid:12.0.0_64only-latest`（64only 镜像）。M 系列 CPU 不支持 32 位 ARM 执行，
混合镜像里的 32 位进程会 `Exec format error`。仓库各处默认已用 64only。

**Q5. `modprobe binder_linux` 失败。**
`binder` 内核模块是 Redroid 的**硬前提**。`host-setup.sh` 会尝试装
`linux-modules-extra-$(uname -r)` 并 `modprobe binder_linux devices="binder,hwbinder,vndbinder"`；
若内核未编译 binder，需换发行版内核或自编内核（PoC D2 红线项）。新内核的 `ashmem` 已被 memfd 取代，
`ashmem_linux` 加载失败可忽略。

**Q6. NVIDIA 显卡跑不了 Redroid 原生 GPU 加速。**
Redroid 硬件渲染走 Intel/AMD 的 Mesa `/dev/dri/render*` 路径（`gpu_mode=host`），
**NVIDIA 闭源驱动不支持此路径**，只能软件渲染（`gpu_mode=guest`）或 QEMU+virtio-gpu（性能损耗大）。
硬件选型据此定，**别照抄甲方的 8×L40S 做渲染**。

**Q7. STF 看不到 redroid 设备。**
STF 原为 USB 物理机设计，纳管 redroid 需让 STF 的 adb 环境先 `adb connect localhost:5555+id`
到容器 TCP 端口。`docker-compose.stf.yml` 用 `network_mode: host` 让 STF 与宿主共享同一个 adb server，
宿主已 `adb connect` 的 redroid 会被 provider 自动注册。
