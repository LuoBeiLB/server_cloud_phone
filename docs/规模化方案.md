# X86 云手机平台 · 规模化（500 台）Kubernetes 预研方案

> 对应计划：**500 台规模化 / k8s（全量方案 D117）**。
>
> ⚠️ **性质声明**：本文与配套清单 `deploy/k8s/*.yaml` 是**设计 / 预研**，**未在真实集群验证**。
> 所有台数、密度、资源数字均为 **`docs/redroid-real-benchmark.md` 单机实测的外推**
> （Apple Silicon → arm64 VM 8G / 软件渲染 / 单实例 ~606 MiB）。正式容量以**目标 Intel/AMD

## 1. 目标与边界

- **规模**：并发 **500 台**云手机（Redroid 实例），支撑「登录 → 批量建机 → 每台开网页 →
  一机一码 → 多画面预览 → 单机/批量操控 → 脚本回放」全链路（与 demo 同一套 API 契约，三端零改动）。
- **形态**：从 demo 的 **Docker Compose（≤20 台）** 演进到 **Kubernetes 多节点**，把「平台服务层」
  与「云手机实例层」拆成两个物理隔离的节点池。
- **不变量**：业务代码 / API / 前端 / App 不改；只改 `orchestrator/redroid.py` 的**下发路径**
  （从「本机 docker.sock + 本机 adb」改为「按节点路由到 device-agent」，见 §6）。
- **本文不含**：等保合规、硬件采购定价、深度风控对抗——留作后续路线图。

## 2. 目标架构（分层）

```
                         ┌──────────────── 接入层 ────────────────┐
   Web(Vue) / PC(Electron) / App(Kotlin)  ──►  Ingress(nginx, WS 升级)
                         └───────────────────┬────────────────────┘
                                             │ /api  /api/ws
                    ┌────────────────────────▼────────────────────────┐
                    │ 平台服务节点池 (cloudphone.io/role=platform)      │
                    │  frontend×2(nginx)   backend×3..20(FastAPI/HPA)  │
                    │  postgres(StatefulSet+PVC)   redis(Pub/Sub 广播)  │
                    │  监控栈: Prometheus / Grafana / Loki             │
                    └───────────────┬─────────────────────────────────┘
                                    │ gRPC/HTTP 下发 + adb-over-tcp
                    ┌───────────────▼─────────────────────────────────┐
                    │ 云手机节点池 (role=phone, gpu=intel-amd)          │
                    │  每节点: redroid-agent(DaemonSet, privileged)    │
                    │          └─ 起 N 台 redroid_{id}(binder+/dev/dri)│
                    │  存储: 本地 NVMe + CoW 母盘快照                    │
                    │  网络: 每台独立出口 IP / 代理位                    │
                    └──────────────────────────────────────────────────┘
```

**两池分治的理由**：平台服务是无状态/有状态的常规负载（可弹性、可迁移）；云手机实例是
**特权 + 内核依赖 + 高密度 + 渲染**的重负载。物理隔离避免二者互相抢 CPU/内存，也把
`privileged` 的安全面收敛在专用节点池（配污点 `cloudphone.io/dedicated=phone:NoSchedule`）。

## 3. 容量估算 / BOM

### 3.1 单实例基线（实测外推）

| 维度 | 实测 / 外推值 | 规划取值 | 依据 |
|---|---|---|---|
| 稳态内存 | ~606 MiB（0.4–1.4% idle CPU） | 内存请求 **1.5 GiB**、上限 **2 GiB**/台（含浏览器 + 波峰 + 系统余量） | benchmark 稳态 RSS |
| 峰值 CPU | 开网页 / 冷启 dex2oat 短时冲高 | **~1 vCPU/台**（峰值，可错峰超卖） | benchmark idle 极低 + 冷启冲高 |
| adb 控制 | 7 ms/次往返 | — | 控制通道低延迟，纳管无瓶颈 |
| 渲染 | 软件（SwiftShader）/ 裸机可 host GPU | 见 §3.3 分档 | VM 无 GPU；生产裸机走 /dev/dri |

### 3.2 参考节点（示例裸机，需按实机回填）

取一台 **32 核 / 64 线程（64 vCPU）、128 GiB RAM、带 Intel/AMD 核显或 Intel Arc/AMD Radeon
（`/dev/dri`）** 的服务器为算例。系统预留（OS + kubelet + 监控 agent + GPU 栈 + 节点代理）≈ **20%**：

- 可分配内存 ≈ 128 × 0.8 ≈ **102 GiB**
- 可分配 CPU ≈ 64 × 0.8 ≈ **51 vCPU**

**单节点台数（取内存维度与 CPU 维度更紧的那个）**：

- 内存维度：稳态 0.6 GiB → 102/0.6 ≈ **170 台**；含波峰规划 1.5 GiB → 102/1.5 ≈ **68 台**
- CPU 维度：峰值 1 vCPU 不超卖 → 51/1 ≈ **51 台**；错峰均摊 0.5 vCPU → ≈ **100 台**

### 3.3 分档结论：软件渲染 vs 裸机 GPU

| 渲染模式 | 瓶颈 | 单节点台数区间 | 典型取值 |
|---|---|---|---|
| **软件渲染**（`gpu_mode=guest`，无 GPU / NVIDIA） | 开网页时 **CPU** 先打满 | **20–40 台/节点** | 30 |
| **Intel/AMD 裸机 host GPU**（`gpu_mode=host`，`/dev/dri`） | 渲染卸载核显 → **内存/调度** | **40–80 台/节点** | 60 |

### 3.4 500 台需多少节点（算式与区间）

```
云手机节点数 = 500 / 单节点台数
  软件渲染:   500/40 ≈ 13   ~   500/20 ≈ 25   → 约 13–25 台（典型 500/30 ≈ 17 台）
  裸机 GPU:   500/80 ≈ 7    ~   500/40 ≈ 13   → 约 7–13 台（典型 500/60 ≈ 9 台）
```

**加基础设施**（与云手机节点物理隔离）：

- 控制面 **3 节点**（HA etcd/apiserver）
- 平台服务 **2–3 节点**（backend 多副本 + postgres + redis + Prometheus/Grafana/Loki）

**BOM 总量区间**：

| 路线 | 云手机节点 | + 控制面 | + 平台 | 合计 |
|---|---|---|---|---|
| 软件渲染 | 13–25 | 3 | 2–3 | **≈ 18–31 节点** |
| 裸机 host GPU | 7–13 | 3 | 2–3 | **≈ 12–19 节点** |

> **头条结论**：500 台约需 **8–25 台云手机节点**（Intel/AMD 裸机 GPU **7–13 台**、软件渲染 **13–25 台**），
> 另加 3 控制面 + 2–3 平台节点。**优先走 Intel/AMD 裸机 + host GPU**，节点数与单台成本都更优。

### 3.5 NVIDIA 坑（硬件选型红线）

Redroid 硬件渲染只认 **Intel/AMD 的 Mesa `/dev/dri/render*`**（`gpu_mode=host`）；**NVIDIA 闭源
驱动不走此路**，只能软件渲染（CPU 密度腰斩）或 QEMU+virtio-gpu（损耗大）。**别照抄甲方
8×L40S 做渲染节点**——渲染型云手机应选带核显的 Intel/AMD 平台或 Intel Arc / AMD Radeon 加速卡。

## 4. 关键工程点

### 4.1 binder 内核模块（硬前提，红线）

Redroid 起不来的头号原因。云手机节点必须 `modprobe binder_linux devices="binder,hwbinder,vndbinder"`
并开机自加载（`deploy/scripts/host-setup.sh` 已封装）。k8s 层面：
- 节点用 DaemonSet 前置校验 / 或节点镜像（Golden Image）内置；`redroid-agent` 挂 `/dev/binderfs`、`/lib/modules`。
- 内核未编译 binder 的发行版直接换内核，属采购/装机阶段红线。新内核 `ashmem` 已被 memfd 取代，可忽略其加载失败。

### 4.2 privileged 安全边界

redroid 实例 / 节点代理需 `privileged: true`（访问 binder 与内核能力），这是全栈**安全面最大**处。收敛手段：
- 只在**专用云手机节点池**开特权（污点隔离，平台负载不上这些节点）；
- 用 PodSecurity（`privileged` 命名空间限于 cloud-phone）、AppArmor/seccomp profile 收窄 syscalls；
- 尽量以「一节点一个特权代理」而非「500 个特权 Pod」暴露特权（见 §6 DaemonSet vs per-instance）。

### 4.3 adb 纳管（后端如何跨节点控制实例）

现状代码假设「后端与实例同机」（本机 docker.sock + `adb connect localhost:5555+id`）。规模化改为：
- **每节点 device-agent**（`redroid-daemonset.yaml`）：在本节点起停 redroid，`hostNetwork` 把每台
  adb 端口 `5555+id` 开在宿主，后端按 `device→node` 路由 `adb connect <nodeIP>:(5555+id)` 或经 agent 转发；
- **STF/DeviceFarmer provider**（`deploy/stf/` 已有 compose 版）：每节点 provider 先 `adb connect`
  本地实例再注册到 STF，投屏（minicap）/控制（minitouch）开箱即用。
- 后端仅需在 `RedroidBackend` 增加「节点地址路由」，API 契约 / DB / 前端零改动。

### 4.4 独立出口 IP / 代理（一机一码）

`fingerprint.py` 已产出 `network.proxy / exit_ip`，`RedroidBackend` 已把 `HTTP_PROXY/HTTPS_PROXY`
注入容器。规模化：
- 代理池经 `CLOUD_PROXY_POOL`（ConfigMap/Secret）或独立密管系统下发，每台分配独立出口位；
- 需要机房级独立公网出口时，配合 SNAT/多拨/代理网关，属网络工程项。

### 4.5 CoW 存储 / 快照（500 台落盘的关键省容量点）

每台 redroid 挂 `/data`（inst{id}）。500 台若各自全量镜像，磁盘暴涨。对策：
- **CoW（写时复制）母盘 + 快照**：以一份「装好 iOS 皮肤 + 基础配置」的母盘为 backing file，
  每台派生只存增量（overlay/btrfs/ZFS snapshot / LVM thin），单台增量常在数百 MiB 级；
- 数据放**本地 NVMe/SSD**（IO 密集），配 StorageClass；重要数据另做备份/生命周期策略。

### 4.6 监控 / 告警：Prometheus + Grafana

- **节点/容器指标**：node-exporter + cAdvisor + kube-state-metrics → Prometheus；
- **实例维度**：redroid-agent 上报「每台 CPU/内存/boot 状态/adb 可达」自定义指标；
- **看板**：Grafana（节点密度、内存水位、每台开机成功率、批量任务耗时）；
- **告警**：节点内存 > 85%、实例 boot 失败率、adb 不可达、代理池耗尽。

### 4.7 日志：Loki

- 平台组件（backend/frontend/pg）日志 + redroid `logcat` 采样经 Promtail → **Loki**，Grafana 统一检索；
- 大规模下 logcat 全量成本高，建议按设备/错误级别采样。

### 4.8 滚动升级 / 弹性扩缩容

- **后端/前端**：Deployment `RollingUpdate`（`maxUnavailable=0`）零停机；WS 长连接缩容窗口拉长（HPA `scaleDown` 300s）。
- **后端弹性**：`hpa.yaml`（CPU/内存起步；建议进阶到 Prometheus Adapter 的「活跃 WS/预览帧 QPS」自定义指标）。
- **云手机节点弹性**：Cluster Autoscaler 按「pending 实例数」增删云手机节点；批量建机前预热（Golden Image + 预拉镜像）缩短冷启。
- **实例升级**：redroid 镜像升级走「新母盘灰度 + 分批重建」，避免一次性重启全部 500 台。

| 里程碑 | 内容 | 产出 / 判据 |
|---|---|---|
| **M0 现状** | Compose：postgres+redis+backend+frontend，simulator/单机 redroid | demo 8 条验收（已达成） |
| **M1 服务上云** | 把 4 个服务搬进 k8s（本目录清单），设备后端先 simulator | `kubectl apply -k` 起栈，主流程通过；确立两节点池标签/污点 |

## 6. DaemonSet（节点池化）vs StatefulSet（有状态卷）取舍

| | **DaemonSet 节点代理（推荐起步）** | **StatefulSet-per-instance（每台一 Pod）** |
|---|---|---|
| 模型 | 每节点 1 个特权代理，代理内批量起停 redroid_{id} | 每台云手机 = 1 个有稳定标识 + PVC 的 Pod |
| 贴合现状 | 高（复用 `orchestrator/redroid.py` 逻辑） | 中（一机一码 props/端口/CoW 卷需逐 Pod 模板化） |
| 特权面 | 小（特权只在 ~10 个代理 Pod） | 大（500 个特权 Pod） |
| 调度/etcd 压力 | 极小（~10 Pod） | 大（500 Pod 对象 + 探测/驱逐） |
| 单台 SLA/迁移 | 弱（实例非一等 K8s 对象，观测靠代理上报） | 强（单台可独立探测/滚动/迁移，卷天然持久） |
| 结论 | **500 台起步首选**：省调度、易复用 | 需「单台可迁移 / 单台 SLA」时再演进 |

> 配套清单 `redroid-daemonset.yaml` 采用 DaemonSet 方案，并在文件尾附了 per-instance StatefulSet
> 的参考骨架（单台 ~1 vCPU / 1.5–2Gi，示例值需按实测实调）。
