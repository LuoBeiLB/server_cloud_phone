## 第 0 章 · 5 分钟决策：先选路径

三条部署路径，按目的选一条，**不要一上来就搞最复杂的**：

| 路径 | 目的 | 环境要求 | 耗时 | 能跑几台云手机 |
|---|---|---|---|---|
| **A · 演示环境** | 给领导看、功能验收、培训 | 任意一台机器（含 Windows / macOS 笔记本），**不需要 Docker 也能跑** | 30 分钟 | 模拟设备，不限台数 |
| **B · 真机单节点** | 真实云手机、性能实测、试点上线 | 1 台 x86 服务器 + Linux（内核支持 binder） | 半天 | 按内存算，见 §1.4 |
| **C · 内网离线** | 机房不通外网 / 信创环境 | 同 B，外加一台能上网的机器做打包 | 1 天 | 同 B |

> **建议顺序**：先跑 A 确认功能符合预期 → 再上 B 做真机与性能验证 → 最后按《规模化方案》扩到多节点。

### 决策速查

```
需要真实安卓、真实装 App？
├── 否 → 路径 A（simulator），任何机器 30 分钟搞定
└── 是 → 机房能访问 Docker Hub / 镜像加速器吗？
         ├── 能 → 路径 B
         └── 不能（内网隔离/信创）→ 路径 C（离线包）
```

## 第 1 章 · 服务器选型（x86 专项）

### 1.1 ⛔ 红线：绝大多数服务器 CPU **没有核显**，会导致无法硬件渲染

这是 x86 服务器部署本项目**最容易踩、也最贵的坑**，请在采购前务必确认。

Redroid 的硬件渲染只走 **Intel/AMD 的 Mesa `/dev/dri` 路径**。而：

| CPU 系列 | 有无集成显卡 | 能否硬件渲染 | 说明 |
|---|---|---|---|
| Xeon Scalable（Platinum / Gold / Silver / Bronze，如 6338、8375C） | ❌ **无核显** | ❌ 只能软件渲染 | **国内机房最常见的服务器 CPU，全系无集成显卡** |
| Xeon E-2300 / E-2400 系列带 `G` 后缀 | ✅ 有（P系核显） | ✅ 可以 | 入门服务器平台，适合云手机节点 |
| Core i7 / i9（工作站 / 定制服务器） | ✅ 有（UHD / Xe） | ✅ 可以 | 单节点密度好，机架形态受限 |
| AMD EPYC | ❌ 无核显 | ❌ 只能软件渲染 | 同 Xeon Scalable |
| AMD Ryzen 带 `G` 后缀 | ✅ 有（Radeon） | ✅ 可以 | — |
| **NVIDIA 显卡（T4 / L40S / A10…）** | 有卡但驱动不兼容 | ❌ **完全走不通** | 闭源驱动不提供 Mesa `/dev/dri` 渲染路径 |

**采购结论（三选一）**：

1. **推荐**：Xeon E-2400 系列带核显平台，或 Core i9 定制服务器 —— 直接有 `/dev/dri`，成本最低。
2. **已有 Xeon Scalable / EPYC 机器**：加装一张 **Intel Arc A310 / A380**（千元级、半高单槽、功耗低）或 **AMD Radeon Pro W 系列**，即可获得 `/dev/dri`。这是存量机器改造的最优解。
3. **接受软件渲染**：不加卡，`CLOUD_REDROID_GPU_MODE=guest`。功能完全可用（开网页、群控、脚本都正常），但单节点密度约腰斩，开网页时 CPU 冲高明显。

**上机第一件事就验证**（30 秒）：

```bash
ls -l /dev/dri/
# 期望看到 renderD128（可能还有 card0）：
#   crw-rw---- 1 root render 226, 128 ... /dev/dri/renderD128
# 如果目录不存在或为空 → 没有可用核显/显卡，只能软件渲染

lspci | grep -iE 'vga|3d|display'   # 看实际图形设备
```

### 1.2 ⛔ 红线：x86 上跑「ARM-only」应用需要转译库

国内大量安卓 App（尤其是中小厂商、游戏）**只发布 ARM 版本**，没有 x86 版本。
x86 服务器上的安卓实例默认**装不上也跑不了这类 App**。

| 场景 | 是否受影响 | 处理方式 |
|---|---|---|
| 只开网页 / 用 WebView（本项目验收场景） | ❌ 不受影响 | 无需处理，Chromium 有原生 x86 版本 |
| 装有 x86/arm64 双版本的主流 App | ❌ 不受影响 | 正常安装 |
| 装 **ARM-only** 的 App | ✅ **受影响** | 需为容器挂载 ARM 转译库（Intel Houdini / NDK Translation） |

> ⚠️ **授权提示**：转译库（libhoudini / libndk_translation）为**专有软件**，商用需另行取得书面授权。
> 挂载方式见 redroid 官方文档的 ARM translation 章节。**本项目交付未包含转译库，也不依赖它。**
> 如果甲方业务必须跑 ARM-only 应用，建议：① 走 ARM 服务器（鲲鹏 / 飞腾 / Ampere）避开转译；
> ② 或先做 App 兼容性摸底，确认必须转译的比例后再决策。请在项目启动前明确这一点。

### 1.3 硬件配置建议

| 部件 | 最低（试点 10–20 台） | 推荐（单节点 40–80 台） | 说明 |
|---|---|---|---|
| CPU | 8 核 16 线程 | **32 核 64 线程** | 按峰值约 1 vCPU/台估算，可错峰超卖至 0.5 |
| 内存 | 32 GB | **128 GB** | 实测单实例稳态 ~606 MiB；生产按 **1.5 GiB/台** 规划留波峰 |
| 系统盘 | 200 GB SSD | 480 GB SSD | 系统 + Docker 镜像 |
| 数据盘 | 500 GB SSD | **2 TB NVMe** | 每实例 `/data` 约 2–6 GB，**必须用 SSD/NVMe**，机械盘会导致启动风暴 |
| 显卡 | 无（软件渲染） | Intel Arc A310/A380 或带核显平台 | 见 §1.1 |
| 网卡 | 千兆 | **万兆** | 多画面预览是带宽大户 |
| 出口 IP | — | 按台数准备代理位 | 见第 7 章 |

### 1.4 单节点能跑多少台（容量速算）

```
台数 = min( 可用内存GB ÷ 1.5 ,  可用vCPU ÷ 峰值vCPU )
       其中 可用资源 ≈ 物理资源 × 0.8（预留 20% 给系统/Docker/监控）
```

| 服务器规格 | 软件渲染 | 硬件渲染（有 /dev/dri） |
|---|---|---|
| 8C16T / 32 GB | 8 – 12 台 | 12 – 16 台 |
| 16C32T / 64 GB | 15 – 25 台 | 25 – 34 台 |
| 32C64T / 128 GB | **20 – 40 台** | **40 – 68 台** |

> 上述为规划区间，**不是承诺值**。机器到位后请用交付包内的压测脚本实测回填：
> `bash deploy/scripts/redroid-benchmark.sh` 与 `bash deploy/scripts/density-test.sh`

### 1.5 云 ECS 还是物理机？

| 形态 | 可行性 | 注意事项 |
|---|---|---|
| **物理裸机** | ✅ 最优 | 内核可控、可插显卡、密度最高。**首选** |
| 云厂商 ECS（阿里云/腾讯云/华为云） | ✅ 可行 | 需选**支持自定义内核模块**的实例；用云厂商官方 Ubuntu 22.04 镜像；无法插显卡故只能软件渲染 |
| 云厂商**弹性裸金属**（神龙 / 黑石） | ✅ 可行 | 兼顾云的弹性与裸机的内核可控性，性价比方案 |
| 托管 K8s 的普通 Node（ACK/TKE 托管节点） | ⚠️ 受限 | 需特权容器 + 内核模块，很多托管节点池不允许；规模化阶段建议用**自建节点池** |
| 容器实例服务（ACI / ECI 等 Serverless 容器） | ❌ 不可行 | 不给内核模块和特权，Redroid 起不来 |

## 第 2 章 · 操作系统与内核（⛔ 头号红线）

### 2.1 Redroid 起不来的第一原因：内核没有 binder

安卓的进程间通信依赖 **binder 内核模块**。宿主机内核没有 binder，Redroid 100% 起不来，且**无法通过任何配置绕过**。

**国内企业最常见的坑：CentOS 7 的内核是 3.10，根本没有 binder。**

| 发行版 | 默认内核 | binder 支持 | 结论 |
|---|---|---|---|
| **Ubuntu 22.04 LTS** | 5.15 | ✅ 装 `linux-modules-extra` 即可 | ✅ **推荐，本项目验证环境** |
| **Ubuntu 24.04 LTS** | 6.8 | ✅ 同上 | ✅ 推荐 |
| Debian 12 | 6.1 | ✅ 通常可用 | ✅ 可用 |
| **CentOS 7** | **3.10** | ❌ **不支持** | ⛔ **不可用，必须换系统** |
| CentOS Stream 9 / Rocky 9 / Alma 9 | 5.14 | ⚠️ 需确认 | 需实测，部分需自编内核 |
| 阿里 Anolis 8 / 腾讯 TencentOS | 4.19 / 5.4 | ⚠️ 需确认 | 需实测 |
| 麒麟 / 统信 UOS（信创） | 视版本 | ⚠️ 需厂商确认 | **必须提前与 OS 厂商确认 binder 可用性**，不要假设 |

> 💡 **给甲方的建议**：如果没有强制的信创要求，**直接用 Ubuntu 22.04 LTS**，这是本项目完整验证过的环境，能省掉大量不确定性。

### 2.2 装机后第一步：验证 binder（2 分钟）

```bash
# 1) 看内核版本（低于 4.x 基本没戏）
uname -r

# 2) 尝试加载 binder 模块
sudo modprobe binder_linux devices="binder,hwbinder,vndbinder"
echo "退出码: $?"        # 0 = 成功

# 3) 确认结果（下面两条命令至少一条要有输出）
lsmod | grep binder
ls -l /dev/binderfs/ 2>/dev/null || ls -l /dev/binder* 2>/dev/null
```

**三种结果的处理**：

| 现象 | 含义 | 处理 |
|---|---|---|
| modprobe 成功 + 有 `/dev/binderfs` | ✅ 通过 | 继续下一步 |
| modprobe 报 `Module not found` | 模块包没装 | `sudo apt install linux-modules-extra-$(uname -r)` 后重试 |
| 装了 extra 仍然失败 | **内核未编译 binder** | ⛔ 换发行版内核，或自编内核（属装机阶段红线，不要试图在应用层绕过） |

### 2.2b ⛔ 红线：内核还必须有 SELinux（selinuxfs），且建议有 cgroup v1 层级

binder 齐全**不代表**能跑起来。Android 的 `init` 启动第一步就要 `mount selinuxfs`，
内核没编译 SELinux 时它会立刻被 SIGHUP 打死。**这个失败非常难查**：

- 容器状态是 `exited`、**退出码 129**
- `docker logs redroid_1` **完全是空的**（还没来得及输出就死了）
- 真正的错误只出现在**宿主机** `dmesg` 里：
  ```
  init: mount("selinuxfs", "/sys/fs/selinux", "selinuxfs", 0, NULL) failed No such file or directory
  cgroup: Unknown subsys name 'memory'
  ```

**上机一并验证**（和 §2.2 的 binder 检查一起做，30 秒）：

```bash
# ① SELinux：两者至少一个要成立
ls -d /sys/fs/selinux            # 存在即可
grep selinuxfs /proc/filesystems # 或内核支持该文件系统

# ② cgroup 层级：cgroup2fs = 纯 v2，Android init 挂 v1 memory 控制器会失败
stat -fc %T /sys/fs/cgroup
```

| 现象 | 处理 |
|---|---|
| `/sys/fs/selinux` 存在，或 `/proc/filesystems` 有 selinuxfs | ✅ 通过 |
| 两者都没有 | ⛔ 内核未编译 SELinux，**应用层无法绕过**。换发行版官方内核（Ubuntu 22.04/24.04 即使默认用 AppArmor 也带 selinuxfs） |
| `stat -fc %T /sys/fs/cgroup` 输出 `cgroup2fs` | ⚠️ 纯 v2。加内核参数 `systemd.unified_cgroup_hierarchy=0` 后重启切回混合层级 |

> ⚠️ **实测记录（2026-07-30）**：在 macOS + **OrbStack** 的 Linux VM（内核 `7.0.11-orbstack`，aarch64）上，
> **binder 三件套齐全**（`/dev/binder`、`/dev/hwbinder`、`/dev/vndbinder`，misc 260/261/262），
> redroid 镜像也正常拉取，但实例仍起不来 —— 卡在缺 `selinuxfs`（外加纯 cgroup v2）。
>
> **结论要分清是「哪个虚拟化」，不是「macOS 不行」**：
>
> | macOS 上的方案 | 内核 | 能否跑真机 |
> |---|---|---|
> | OrbStack / Colima / Docker Desktop | 各自的裁剪内核，**无 SELinux** | ❌ 不行 |
> | **Lima + Ubuntu 官方镜像** | 发行版内核，`CONFIG_SECURITY_SELINUX=y` | ✅ **实测可跑** |
>
> 同日在 Lima 起的 Ubuntu 26.04（内核 `7.0.0-28-generic`，aarch64）上实测跑通：
> `modprobe binder_linux` 后挂 binderfs，redroid 正常开机 —— Android 12 / SDK 31 /
> arm64-v8a / 80 进程 / 96 个应用包 / 单实例约 1 GiB。macOS 开发机一键脚本见
> [§5.3c](#53c-macos-开发机一键起真机)。生产交付仍走 x86_64 Linux（路径 B）。
>
> 管理端「系统自检」已包含 selinuxfs 与 cgroup 两项检查，会直接报出原因与处置。
> 注意：后端跑在容器里时这两项显示为「无法判定」（容器命名空间看不到宿主内核设施），
> 请按提示在**宿主机上**用上面的命令确认。

### 2.3 让 binder 开机自动加载

```bash
echo "binder_linux" | sudo tee /etc/modules-load.d/redroid-binder.conf
echo "options binder_linux devices=binder,hwbinder,vndbinder" | sudo tee /etc/modprobe.d/redroid-binder.conf
```

> 交付包内的 `deploy/scripts/host-setup.sh` 已封装上述全部步骤（含校验与失败提示），见 §5.2。

## 第 3 章 · 国内网络环境准备（🇨🇳 核心章节）

> **本章是国内部署与海外部署差异最大的地方，请完整执行。**
> 不做镜像加速，`docker pull` 一个 800 MB 的 redroid 镜像可能要几小时甚至直接超时失败。

### 3.1 先判断你的网络场景

```bash
# 测试 Docker Hub 直连（10 秒内有响应算通）
curl -s -m 10 -o /dev/null -w "Docker Hub: %{http_code}  耗时 %{time_total}s\n" https://registry-1.docker.io/v2/

# 测试 GitHub（下载 Lawnchair APK 等资产要用）
curl -s -m 10 -o /dev/null -w "GitHub:     %{http_code}  耗时 %{time_total}s\n" https://github.com
```

| 结果 | 场景 | 走哪一节 |
|---|---|---|
| 都通且快 | 网络良好（少见） | §3.2 配好加速器保底即可 |
| 通但极慢 / 时断时续 | **国内绝大多数情况** | §3.2 + §3.3 + §3.4（必做） |
| 完全不通 | 内网隔离 / 信创机房 | 跳到 **第 6 章 离线部署** |

### 3.2 Docker 镜像加速（🇨🇳 必做）

> ⚠️ **重要提醒**：2024 年 6 月起，国内大量公共镜像加速器（中科大、网易、DaoCloud 公共节点等）
> 陆续**关停或限流**，且变动频繁。**不要盲目照抄网上的地址列表**，务必用 §3.4 的自检命令实测后再用。

按可靠性排序，**企业环境建议选 1 或 2**：

#### 方案 1（最佳）：云厂商专属加速器 —— 服务器在公有云上时

服务器在哪家云，就用哪家的加速器，走内网，速度最快且免费：

| 云厂商 | 获取方式 | 地址形态 |
|---|---|---|
| 阿里云 | 控制台 → 容器镜像服务 ACR → 镜像加速器 | `https://<你的专属ID>.mirror.aliyuncs.com` |
| 腾讯云 | 无需申请，**仅腾讯云 VPC 内可用** | `https://mirror.ccs.tencentyun.com` |
| 华为云 | 控制台 → 容器镜像服务 SWR → 镜像中心 | 控制台给出专属地址 |

#### 方案 2（企业推荐）：自建 Harbor 私有仓库

一次性从外网把镜像同步进来，之后所有节点都从内网 Harbor 拉，**速度快、可控、可审计**，也是后续 500 台规模化的必备设施。

```bash
# 在一台能出网的机器上（或用第 6 章的离线包）
docker pull redroid/redroid:12.0.0-latest
docker tag  redroid/redroid:12.0.0-latest harbor.your-company.com/cloudphone/redroid:12.0.0
docker push harbor.your-company.com/cloudphone/redroid:12.0.0

# 各节点配置后端使用私有地址
export CLOUD_REDROID_IMAGE=harbor.your-company.com/cloudphone/redroid:12.0.0
```

#### 方案 3（临时）：第三方公共加速器

可用性不稳定、随时可能失效，**仅建议用于快速验证，不要写进生产运维手册**。
配置前请务必用 §3.4 实测。

#### 配置方法（三种方案通用）

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": [
    "https://你的专属ID.mirror.aliyuncs.com"
  ],
```

### 3.3 Docker CE 安装（🇨🇳 国内源）

**不要用** `curl -fsSL https://get.docker.com | sh` —— 在国内经常卡住或失败。用阿里云源：

```bash
# ---- Ubuntu 22.04 / 24.04 ----
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
https://mirrors.aliyun.com/docker-ce/linux/ubuntu $(lsb_release -cs) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

sudo systemctl enable --now docker
sudo usermod -aG docker $USER      # 免 sudo 用 docker，需重新登录生效
docker --version && docker compose version
```

**同时把 apt 源也换成国内镜像**（Ubuntu 22.04 示例）：

```bash
sudo cp /etc/apt/sources.list /etc/apt/sources.list.bak
sudo sed -i 's@//.*archive.ubuntu.com@//mirrors.aliyun.com@g; s@//.*security.ubuntu.com@//mirrors.aliyun.com@g' \
  /etc/apt/sources.list
sudo apt-get update
```

> Ubuntu 24.04 的源文件在 `/etc/apt/sources.list.d/ubuntu.sources`，改法类似（把 `URIs:` 行换成 `https://mirrors.aliyun.com/ubuntu/`）。

### 5.3 ⛔ 选对 redroid 镜像（x86 必改项）

**代码仓库的默认镜像是为 ARM 开发环境（Apple Silicon）选的，上 x86 服务器必须改。**

| 镜像 tag | 架构 | ABI | x86 服务器适用性 |
|---|---|---|---|
| `redroid/redroid:12.0.0-latest` | amd64 + arm64 | 32 位 + 64 位 | ✅ **x86 生产推荐**，兼容性最好 |
| `redroid/redroid:12.0.0_64only-latest` | amd64 + arm64 | 仅 64 位 | ⚠️ 仓库默认值，为 Apple Silicon 选（该平台无 32 位 ARM 支持）；x86 上可跑但丢失 32 位 ABI |
| `redroid/redroid:13.0.0-latest` / `14` / `15` | amd64 + arm64 | 32+64 | 可选更高版本，**换版本需重新验证皮肤落地流程** |

> 已实测确认：redroid 官方全部 tag 均为 `amd64+ arm64` 多架构，x86_64 服务器可直接拉取。
> Android 12 标准镜像 amd64 压缩体积约 **769 MB**，64only 约 **616 MB**。

### 5.3c macOS 开发机一键起真机

macOS 上的 OrbStack / Docker Desktop 跑不了真机（§2.2b），但 **Lima + Ubuntu 可以**。
仓库提供了一键脚本，它会在 Ubuntu VM 里执行**与生产完全相同**的那条 compose 命令：

```bash
bash deploy/scripts/dev-up-real.sh          # 起（首次建 VM 约 3–5 分钟）
bash deploy/scripts/dev-up-real.sh --down   # 停服务，保留 VM 与镜像
bash deploy/scripts/dev-up-real.sh --destroy # 连 VM 一起删

# 国内网络：把 Mac 上的代理透给 VM 内的 docker
PROXY=http://127.0.0.1:7897 bash deploy/scripts/dev-up-real.sh
```

脚本做的事：建/启 Lima Ubuntu VM → 加载 `binder_linux` 并挂 binderfs → 装 docker/adb →
（可选）用 **SSH 反向隧道**把 Mac 的代理送进 VM → 在 VM 内 `docker compose up -d --build`
→ 建 SSH 正向隧道把 `5173`/`8000` 转回 Mac。完成后浏览器开 `http://localhost:5173`。

> 两个实测坑，脚本已规避：
> ① 不能让 VM 直连 `host.lima.internal` 用 Mac 的代理 —— Lima 的用户态网关会接受 TCP 握手
> （看起来"可达"）却转发不到 Mac 的 `127.0.0.1`，docker 报
> `proxyconnect tcp: dial tcp 192.168.5.2:7897: i/o timeout`。必须用 SSH 反向隧道。
> ② Lima 的自动端口转发对 docker 发布的 `0.0.0.0` 端口不总是生效，需显式建正向隧道。

> **为什么不用 compose 注释里的 `network_mode: host`**：host 网络下的 backend 不在 compose
> 的桥接网上，前端 nginx 的 `proxy_pass backend:8000` 就解析不到，整个栈会断。
> 覆盖层改用 `CLOUD_REDROID_ADB_MODE=container`，后端通过 docker 网络内的容器名
> `adb connect redroid_<设备ID>:5555` 连实例，**不需要 host 网络**。
>
> `CLOUD_REDROID_NETWORK` 要与实际网络名一致（默认 `cloud_default` = 仓库目录名 + `_default`）。
> 目录改名或用了 `docker compose -p` 时，用 `docker network ls` 确认后同步修改。

起完后先开管理端「系统自检」：binder、selinuxfs、cgroup、redroid 镜像、docker.sock、
内存、磁盘会逐项报出状态与处置；设备若拉不起来，设备列表「状态」列的红色图标悬浮即可
看到完整的「原因 ｜ 处置 ｜ 证据（含容器退出码与日志尾部）」。

### 7.2 IP 资源方案对比

## 第 11 章 · 常见问题排查 FAQ

### 🩺 出任何问题，先开「系统自检」

管理控制台左侧菜单 **系统自检**（或直接访问 `http://服务器IP:5173/#/diagnostics`）。
它会逐项实测并**直接给出该敲的命令**：数据库、Redis、Docker daemon、redroid 镜像、
内核 binder、`/dev/dri`、adb、磁盘、内存、以及「库里说在跑但容器已经没了」的设备。
需要动手的项排在最前面，处置命令可一键复制。**比翻日志快得多，请先看这里。**

两点说明：

- 标为「**无法判定**」的项（通常是 binder、`/dev/dri`）不是故障。后端跑在容器里时，宿主机
  的内核设施在容器内本来就看不见，所以不能据此断定宿主缺失 —— 按该项提示在宿主机上直接
  `ls` 确认即可。
- 如果**连自检页都打不开**，说明问题在更外层。此时用免鉴权的健康探针：
  ```bash
  curl -s --noproxy '*' http://localhost:5173/api/health
  # {"status":"ok",...}          → 后端正常，问题在前端资源（试强制刷新 Ctrl/Cmd+Shift+R）
  # {"status":"degraded",...}    → 数据库不可用，按返回的 hint 处理
  # HTTP 502 / 无响应            → 请求没到后端，见下面 Q1b
  ```

**设备「状态：异常」怎么看原因**：设备列表「状态」列会有红色感叹号，鼠标悬浮即显示完整的
「原因 ｜ 处置 ｜ 证据」（含容器退出码与容器日志尾部），不需要 ssh 上服务器 `docker logs`。

---

**Q1b：所有 `/api` 请求都是 502，但 backend 容器是 healthy**
请求没到后端。最常见的成因是**只重新发布了 backend**：容器重建会拿到新 IP，而 nginx 的
`upstream` 块只在配置加载时解析一次 DNS，于是一直连旧 IP。
```bash
docker inspect cloud_backend --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
docker exec cloud_frontend getent hosts backend    # 两个 IP 不一致 = 中招
docker exec cloud_frontend nginx -s reload         # 立刻恢复
```
本项目已改用 `resolver` + 变量形式 `proxy_pass` 让 nginx 按 TTL 重新解析（见
`deploy/nginx/default.conf`），新版本不会再出现。若你的前端镜像是旧版本，用上面的 reload
应急，并尽快重建前端镜像。

**Q1c：管理页面能打开，但点击操作没反应**
先看浏览器 F12 → Console 第一行。三种典型：
- `Failed to fetch dynamically imported module` → 浏览器缓存了旧的 `index.html`，引用的
  资源在新镜像里已不存在。强制刷新（Ctrl/Cmd+Shift+R）。新版本前端会自动识别并刷新一次。
- 完全没有新的网络请求 → 前端 JS 层就断了，同上先强刷。
- 有请求但 4xx/5xx → 后端问题，看状态码；新版本会把原因与处置直接弹在界面上。

### 🇨🇳 国内网络类

**Q1：`docker pull` 报 `TLS handshake timeout` 或卡住不动**
加速器失效或未生效。按顺序排查：
```bash
docker info | grep -A3 "Registry Mirrors"     # 确认加速器已配上
sudo systemctl restart docker                  # 改完 daemon.json 必须重启
```
仍不行就换加速器方案（§3.2），或走离线包（第 6 章）。

**Q2：装前端依赖报 TLS / 证书错误（`ERR_SSL_SSLV3_ALERT_BAD_RECORD_MAC`）**
没换源。执行 `pnpm config set registry https://registry.npmmirror.com` 后重试；
corepack 拉 pnpm 本体也要 `export COREPACK_NPM_REGISTRY=https://registry.npmmirror.com`。
这是本项目实测踩过的坑，**必现**。见 §3.6。

**Q2a：`docker pull` 正常，但 `docker compose --build` 报 `failed to fetch anonymous token`**
先手工把基础镜像拉下来，再构建：

```bash
docker pull python:3.12-slim && docker pull node:22 && docker pull nginx:alpine
docker compose up -d --build --wait      # 此时 BuildKit 直接用本地镜像，不再访问 registry
```

原因：**BuildKit 不继承 dockerd 的 proxy 设置**（`docker info` 里的 HTTPProxy 只作用于
dockerd 自身）。所以配了 daemon 代理后 `docker pull` 能通，`compose --build` 解析
`FROM` 时却仍直连 registry 而失败。配 §3.2 的 `registry-mirrors` 不受此影响
（镜像加速器是 daemon 配置，BuildKit 会读），**企业环境优先用加速器而非代理**。

> 实测踩过的坑：出网被 DNS 污染时，`auth.docker.io` 会被解析到 Dropbox / Facebook /
> Twitter 的地址段（`108.160.x`、`157.240.x`、`199.59.x`），于是 TCP 能连上、TLS 必然失败，
> 报错是 `dial tcp <无关IP>:443: i/o timeout`。看到无关网段的 IP 就说明是 DNS 被污染，
> 不要在网络层反复重试，直接配加速器。

**Q2b：`docker build` 报 `cannot replace to directory .../node_modules/xxx with file`**
宿主 `frontend/node_modules` 被 COPY 进了镜像——pnpm 的软链接去覆盖镜像内 npm/pnpm 装出的真实目录。
根 `.dockerignore` 已排除 `**/node_modules`；若仍复现，确认该文件存在且构建时未被 `-f` 指到别的上下文。

**Q2c：`pnpm install` 报 `ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite`**
Node 版本太低。pnpm 11 要求 **Node ≥ 22.13**，`node -v` 确认后升级。

**Q3：`pip install` 极慢或超时**
换清华/阿里源，见 §3.5。

**Q4：`fetch-lawnchair.sh` 下载失败**
GitHub 不通。走 §8.1 的方式二（代理）或方式三（离线拷贝）。

### ⛔ 内核与容器类

**Q5：`modprobe binder_linux` 报 `Module not found`**
```bash
sudo apt install -y linux-modules-extra-$(uname -r)
sudo modprobe binder_linux devices="binder,hwbinder,vndbinder"
```
装了 extra 还失败 → 内核未编译 binder，**必须换内核/换发行版**，无法绕过（见第 2 章）。

**Q6：容器起来了但安卓一直起不来 / 反复重启**
```bash
docker logs redroid_1 --tail 100
```
- 报 `Exec format error` → 镜像架构不对，确认拉的是 amd64（`docker inspect` 看 Architecture）
- 报 binder 相关 → 回到第 2 章
- 卡在 boot → 磁盘太慢（务必用 SSD/NVMe）或内存不足

**Q6b：`cloud_backend` 反复重启，日志报 `relation "users" does not exist`**
已修复（`backend/app/database.py`）。原因是建表与幂等补列 DDL 同事务，Postgres 下补列失败会
把建表一起回滚。若在旧版本上遇到，升级代码后 `docker compose down -v && docker compose up -d` 重建。

**Q6c：`cloud_frontend` 恒为 `unhealthy`，但浏览器能正常打开**
健康检查探针地址用了 `localhost`。容器内 `localhost` 会同时解析到 `::1`，而 nginx 的
`listen 80` 只绑 IPv4，BusyBox wget 先试 IPv6 就 Connection refused。
`docker-compose.yml` 已改用 `http://127.0.0.1:80/`。同理，宿主侧自测也要用 `127.0.0.1:5173`
而非 `localhost:5173`（macOS 下 localhost 优先走 ::1）。
另注意：若配了 `http_proxy`，`curl` 会把 `127.0.0.1` 也送进代理导致 502，自测加 `--noproxy '*'`。

**Q7：设备一直卡在「创建中」**
adb server 卡死（本项目实测过的坑）：
```bash
sudo adb kill-server
sudo adb start-server
sudo systemctl restart cloudphone-backend
```

**Q8：设备失联（管理台报「设备 N 已失联」/ 接口返回 503）**

设备的 adb 通道断了。触发场景：宿主机休眠或重启、adb server 被重启、容器重建后端口变化。

**平台会自动自愈**：任何一次设备操作遇到通道断开，都会自动重连并重试一次（约 2 秒内完成），
多数掉线无需人工介入。只有**重连也失败**（容器真的停了/崩了）才会报 503。

收到 503 时按下面排查：

```bash
# ① 容器还在跑吗（端口 = 5555 + 设备ID）
docker ps -a --format "{{.Names}}\t{{.Status}}\t{{.Ports}}" | grep redroid

# ② 容器不在 → 起回来
docker start redroid_6

# ③ 容器在跑但仍失联 → 手工连一次看报什么
adb connect localhost:5561
adb -s localhost:5561 get-state        # 期望输出 device

# ④ adb server 本身卡住（少见）
sudo adb kill-server && sudo adb start-server
sudo systemctl restart cloudphone-backend
```

**一键巡检**：`python acceptance_live.py`（非破坏性，不建机不删机）会逐台核验并给出结论，
§5 还会专门检出「有画面但其实是失联」的伪装情况。**建议纳入日常巡检。**

> 📌 **历史问题（已于 v1.1 修复，用旧版本务必了解）**：早期版本 adb 失败会**静默降级** ——
> 取帧失败回退成平台渲染的皮肤图（预览里那格看着完全正常）、批量操作把失联设备计入成功、
> 应用/日志/文件列表返回空（显示成「没有应用」而非「读不到」）。
> 现已全部改为明确报错：失联 → 503、命令失败 → 502，且预览会实时推送失联状态。
> 若你部署的是旧版本，看到「画面正常但操控没反应、应用数为 0」就是这个问题，请升级。

**Q9：宿主机重启后设备都没了**
容器已配 `restart_policy=unless-stopped` 会自动拉起，但需确认：
```bash
lsmod | grep binder          # binder 是否随开机加载（§2.3）
docker ps -a                  # 容器是否在
sudo systemctl status cloudphone-backend
```

注意换肤要**重启一次容器**，全过程 40–90 秒，控制台有实时进度条。

**Q14：实时预览不动 / 换肤进度不显示**
WebSocket 没通。检查 Nginx 的 `/api/ws` 是否配了 `Upgrade` 头（§5.7），
以及是否有中间设备（WAF / 负载均衡）掐断了长连接。

**Q15：装 App 提示不支持的架构**
ARM-only 应用在 x86 上的固有问题，见 §1.2。

**Q16：网页打开后一直空白 / 显示无数据**

正常情况下登录态失效会**自动提示「登录状态已失效，请重新登录」并跳回登录页**，不会卡在空白页。

若仍然空白：
1. 打开浏览器开发者工具（F12）看 Network，确认接口返回码；
2. 全是 401 → 登录态问题，`Ctrl+Shift+R` 强刷或清站点数据后重新登录；
3. 接口 502/503 → 是后端或设备侧的问题，看 Q8；
4. 接口根本没发出去 → 检查 Nginx 的 `/api` 反代是否配好（§5.7）。

> 📌 **历史问题（已于 v1.1 修复）**：早期版本 token 过期后会**卡在空白页且无任何提示** ——
> 拦截器只清了浏览器本地 token 没清前端状态，导致路由守卫仍认为已登录、把登录页又弹回去。
> 旧版本遇到这个只能手工清站点数据。
